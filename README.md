# MJPEG Stream Service

Сервис на платформе .NET для одновременного получения и отображения нескольких видеопотоков формата MJPEG с публичного сервера Macroscop в браузере. Цель была написать простой сервис с минимальный UI (только плеер, без кнопок и тд.) для практики ASP.NET и Blazor.

## Схема работы

Взаимодействие: Macroscop API → Сервер → Браузер

1. При открытии главной страницы сервер запрашивает список активных камер у Macroscop, фильтрует отключённые каналы и подставляет их ID в теги <img> на странице.
2. Каждый <img> обращается не к внешнему серверу, а к эндпоинту /stream?channelId=N.
3. Сервер открывает потоковое соединение к Macroscop, получая видеопоток, и пересылает их браузеру через бесконечный HTTP-ответ.
4. При закрытии вкладки браузером соединение к Macroscop автоматически разрывается через CancellationToken.


## Аргументация выбора технологий и рассмотренные альтернативы

### 1. Серверная часть: ASP.NET Core Minimal API 
В сервисе обращение идет лишь на один маршрут, поэтому было принято решение выбрать Minimal API за его простоту, компактность прямой доступ к HTTP контексту, заголовкам и управлению буферизацией.
* **Альтернативы:**
  * **ASP.NET Core MVC:** избыточен для одного маршрута и не даёт плюсов для этой задачи.
  * **gRPC:** не позволяет отображать видео в теге <img> без дополнительных преобразований MJPEG-потока.

### 2. Клиентская часть: Blazor
* Такой выбор позволяет написать сервер и клиент на одном языке без отдельной настройки фронтенда.
* Страница собирается на сервере один раз при открытии: получает список камер и отдаёт обычный HTML. Браузер сам умеет проигрывать поток формата multipart/x-mixed-replace внутри тега <img>, поэтому не нужны кнопки управления и JS-скрипты.
* **Альтернативы:**
  * **Отдельный JS-фреймворк:** потребовал бы отдельной настройки сборки фронтенда, что не подходит под минимальные требованиях к UI.
  * **Blazor WebAssembly:** требует скачивать .NET для работы на клиенте, из-за чего дольше грузится. Невозможность работать с бесконечным потоком данных и проблемы с CORS.

### 3. Межсерверное и клиент-серверное взаимодействие: Typed HttpClient
  * Использует IHttpClientFactory, обеспечивая переиспользование сетевых соединений и единую настройку BaseAddress, заголовка Authorization.
  * HttpCompletionOption.ResponseHeadersRead буферизовать начинает чтение сразу после получения HTTP-заголовков.
  * CopyToAsync передаёт поток байтов небольшими буферами  клиенту с минимальным расходом памяти.
* **Альтернативы:**
  * **WebSockets:** лишние проблемы в виде парсинга multipart разделителей, вырезании JPEG-кадров и использовании JS. Браузер уже умеет работать с MJPEG потоком через img.
  * **Server-Sent Events (SSE):** бинарные кадры пришлось бы кодировать в Base64 и декодировать на клиенте через JS.

## Структура проекта

* `Program.cs` — регистрация сервисов, настройка `HttpClient`, конфигурация конвейера и эндпоинт `/stream`.
* `ApiOptions.cs` — настройки подключения к Macroscop и количества выводимых камер.
* `Models/` — модели для десериализации ответа `/configex` (ConfigexResponse, Channel).
* `Services/` — интерфейс `IStreamApiService` и реализация `StreamApiService` для работы с API Macroscop.
* `Components/Pages/Home.razor` — главная страница, запрашивающая активные камеры и отрисовывающая плееры <img>.
* `appsettings.json` — параметры подключения (URL, логин, пароль, количество потоков).
