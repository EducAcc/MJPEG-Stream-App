# MJPEG Stream Service

Сервис на платформе .NET для одновременного получения и отображения нескольких видеопотоков формата MJPEG с публичного сервера Macroscop в браузере. Цель проекта — реализовать простой и надёжный сервис с минимальным UI (только плееры без кнопок и стилей) для практики ASP.NET Core и Blazor.

## Схема работы

Взаимодействие: **Macroscop API → Сервер (.NET) → Браузер**

1. При открытии главной страницы сервер запрашивает список активных камер у Macroscop, фильтрует отключённые каналы и подставляет их ID в теги `<img>` на странице.
2. Каждый `<img>` обращается не к внешнему серверу, а к локальному эндпоинту /stream?channelId=<id>.
3. Сервер открывает потоковое соединение к Macroscop и по мере поступления байтов пересылает видеопоток браузеру через «бесконечный» HTTP-ответ.
4. При закрытии вкладки браузером соединение к Macroscop автоматически разрывается через CancellationToken.

## Аргументация выбора технологий и рассмотренные альтернативы

### 1. Серверная часть: ASP.NET Core Minimal API
В сервисе используется лишь один API-маршрут для стриминга, поэтому был выбран Minimal API за его простоту, компактность, прямой доступ к HTTP-контексту, заголовкам и управлению буферизацией.
* **Альтернативы:**
  * **ASP.NET Core MVC:** избыточен для одного маршрута и не даёт преимуществ для этой задачи.
  * **gRPC:** не позволяет отображать видео в теге `<img>` без промежуточного преобразования готового MJPEG-потока.

### 2. Клиентская часть: Blazor
Такой выбор позволяет написать сервер и клиент на одном языке без отдельной настройки сборки фронтенда.
* Страница собирается на сервере один раз при открытии: получает список камер и отдаёт обычный HTML. Браузер сам умеет проигрывать поток формата multipart/x-mixed-replace внутри тега `<img>`, поэтому не нужны кнопки управления и JS-скрипты.
* **Альтернативы:**
  * **Отдельный JS-фреймворк (React / Vue):** потребовал бы отдельной настройки сборки фронтенда и CORS, что избыточно при минимальных требованиях к UI.
  * **Blazor WebAssembly:** заставляет браузер скачивать .NET для работы на клиенте, из-за чего страница дольше открывается, при этом сервер-прокси всё равно обязателен для скрытия данных авторизации, обхода CORS и выполнения схемы задания.

### 3. Межсерверное и клиент-серверное взаимодействие: потоковый HTTP-запрос и Typed `HttpClient`
* Типизированный HttpClient использует IHttpClientFactory, обеспечивая переиспользование сетевых соединений и единую настройку BaseAddress и заголовка Authorization.
* HttpCompletionOption.ResponseHeadersRead позволяет не ждать окончания «бесконечного» ответа, начиная чтение сразу после получения HTTP-заголовков.
* CopyToAsync передает поток байтов небольшими буферами клиенту с минимальным расходом памяти.
* **Рассмотренные альтернативы:**
  * **WebSockets:** потребовали бы ручного парсинга multipart разделителей, вырезания отдельных JPEG-кадров на сервере и отрисовки через JS на клиенте. Браузер уже умеет проигрывать MJPEG-поток через `<img>`.
  * **Server-Sent Events (SSE):** рассчитаны на текстовые данные, поэтому бинарные кадры пришлось бы кодировать в Base64 и декодировать на клиенте через JS.

## Структура проекта

* `Program.cs` — регистрация сервисов, настройка `HttpClient`, конфигурация конвейера и эндпоинт `/stream`.
* `ApiOptions.cs` — настройки подключения к Macroscop и количества выводимых камер.
* `Models/` — модели для десериализации ответа `/configex` (`ConfigexResponse`, `Channel`).
* `Services/` — интерфейс `IStreamApiService` и реализация `StreamApiService` для работы с API Macroscop.
* `Components/Pages/Home.razor` — главная страница, запрашивающая активные камеры и отрисовывающая плееры `<img>`.
* `appsettings.json` — параметры подключения (URL, логин, пароль, количество потоков).
